# Relatório de Execução — 2026-05-09

## Resumo das Atividades
Nesta sessão, o foco principal foi **estabilizar a persistência de dados no Workspace de Engenharia do Kurupira**, garantindo que as edições de projeto fluíssem corretamente do frontend até o banco de dados.

### 1. Resolução do "Falso Positivo" de Salvamento (UI Mocks)
- **Problema:** O botão de salvar projeto no `EngineeringNavigation.tsx` utilizava um `setTimeout` para simular uma chamada de rede (`saving` → `success`), mas nunca invocava o serviço real de salvamento. O usuário clicava, recebia o feedback visual de sucesso, mas os dados eram perdidos ao recarregar.
- **Solução:** Erradicação do mock. O botão foi conectado diretamente ao `ProjectService.saveDesign(null)`. O gerenciamento de estados (`saving`, `success`, `error`) agora reflete a promessa real retornada pelo backend.

### 2. Implementação do Padrão "Merge-on-Save" (Cadeia da Verdade)
- **Problema:** Havia um drift arquitetural: as coordenadas (`latitude`, `longitude`) existiam fisicamente na tabela `TechnicalDesign`, mas o motor de engenharia usava a propriedade aninhada `designData.solar.clientData`. Quando a UI enviava os dados, os campos físicos ficavam obsoletos.
- **Solução:** Implementação do padrão *Merge-on-Save* no `designs.js` (Kurupira Backend). Agora, antes do Prisma executar a query de `update`, o backend intercepta o JSON, extrai as variáveis `lat`/`lng` contidas nele e sobrescreve as colunas físicas relacionais. O JSON atua como o **Master Data** do domínio de engenharia.

### 3. Registro no Caderno de Campo
- Criação da **Seção 13** no `docs/manual_boas_praticas.md`, consolidando as lições aprendidas:
  - Documentação da obrigatoriedade do *Merge-on-Save* para dados meta-espaciais.
  - Regra de ouro proibindo estritamente a manutenção de "mocks visuais de rede" em botões de mutação de estado.

### 4. Criação da Skill `mock-sweeper`
- Desenvolvimento de uma skill dedicada (`.agent/skills/mock-sweeper/SKILL.md`) voltada a caçar dívidas técnicas de interface: falsos positivos, loaders sem await e botões de timeout que mentem sucesso.
- **Auditoria Kurupira:** Execução imediata da skill no Frontend do Kurupira. Todos os componentes (`ProjectFormModal`, `CatalogEditor`, `SettingsModule`) foram vistoriados e certificados como limpos (utilizando chamadas reais à API). Os `setTimeout` restantes restringem-se apenas a limpezas estéticas temporárias (esconder toasts após N segundos).

## Impacto
O fluxo de ponta-a-ponta (State Zustand → Payload JSON → Axios → Backend Express → Validação Zod → Prisma → DB) está inteiramente desobstruído. Engenheiros já podem montar diagramas, preencher demandas de carga e confiar que seus inputs estarão persistidos no MySQL.

## Sessão 2 — Deploy, Estabilização e Documentação de Lições de Produção

### 1. Promoção de Colunas Estruturadas no Schema (Cadeia da Verdade no DB)
- **Contexto:** Campos como `clientName`, `city`, `state`, `averageConsumption` e `targetPowerKwp` existiam apenas dentro do JSON `designData`, dificultando consultas SQL e a exibição nos painéis do Sumaúma.
- **Solução:** Promoção para colunas físicas no modelo `TechnicalDesign` (Prisma). O `NexusClient` e `ProjectService.ts` foram atualizados para garantir que o payload de salvamento respeite o novo contrato de dados estruturados.

### 2. Mock Sweeper — Orientação de Módulo Conectada ao Motor Real
- **Problema:** Os botões de orientação de módulo na `ArrangementToolbar.tsx` executavam apenas `() => {}` (callbacks vazios), sem impacto no estado Zustand.
- **Solução:** Conexão dos botões ao `engineeringSlice` via `setModuleOrientation()`. O motor `autoLayoutArea` foi refatorado para ler `moduleOrientation` e `moduleSpacingM` do estado global, tornando o layout determinístico e controlado pela intenção do usuário.
- **Adição ao `ProjectService`:** Campos `moduleOrientation` e `moduleSpacingM` incluídos nos objetos de reset para garantir conformidade com o novo schema de `EngineeringInput`.

### 3. Deploy Completo em Produção (VPS Locaweb)
- **Commits:** `229f1a3` (alterações arquiteturais) e `0f067a3` (fixes TypeScript) publicados.
- **Backend:** Containers `neonorte_kurupira` e `neonorte_admin` reconstruídos e subidos. Status final: `Up (healthy)`.
- **Schema DB:** Sincronizado via `docker exec neonorte_kurupira ./node_modules/.bin/prisma db push` — `The database is already in sync with the Prisma schema`.

### 4. Incidente de Produção: HTTPS Derrubado por Nginx (Post-mortem)
- **Causa:** O comando `sudo cp vps.conf /etc/nginx/sites-available/ywara` sobrescreveu os blocos SSL (`listen 443 ssl`) adicionados pelo Certbot ao config do servidor.
- **Sintoma:** `ERR_CONNECTION_REFUSED` em todas as requisições HTTPS. O Nginx estava rodando, mas porta 443 não tinha listener.
- **Resolução:** `sudo certbot --nginx -d kurupira.neonorte-ywara.tech -d admin.neonorte-ywara.tech` — certificado reemitido e blocos SSL restaurados automaticamente.
- **Prevenção implementada:**
  - `vps.conf` local recebeu aviso crítico no cabeçalho proibindo `cp` direto.
  - Playbook 4 da skill `vps-deploy` atualizado com passo obrigatório do Certbot após qualquer cópia do config.

### 5. Correção de Cache Nginx para Deploys Visíveis Automaticamente
- **Problema:** Nginx sem `Cache-Control` no `index.html` → browser (e Workbox SW) serviam bundle antigo indefinidamente.
- **Solução:** `vps.conf` atualizado com estratégia dual:
  - `index.html` → `Cache-Control: no-store, no-cache` (sempre buscado do servidor)
  - Assets com hash Vite (`*.js`, `*.css`, fontes) → `Cache-Control: public, immutable; expires 1y` (cache máximo, já que o hash muda a cada build)

### 6. Incidente: `*.tsbuildinfo` Bloqueando `git pull` no VPS (Post-mortem)
- **Causa:** `tsconfig.tsbuildinfo` estava versionado no Git. O build no VPS gerava uma versão diferente do arquivo, causando `git pull` abortado na próxima sessão.
- **Consequência silenciosa:** O build executava com o código antigo → mesmo hash de bundle → Workbox SW não detectava mudança → deploy invisível para o usuário.
- **Resolução:** `git checkout sumauma/frontend/tsconfig.tsbuildinfo && git pull` + rebuild produziu hash diferente → Workbox auto-atualizou sem intervenção do browser.
- **Prevenção implementada:**
  - `*.tsbuildinfo` adicionado ao `.gitignore` raiz.
  - Playbook 5 da skill `vps-deploy` blindado com `git checkout *.tsbuildinfo` antes do pull.
  - Armadilha #4 documentada na skill.

### 7. Documentação Consolidada no Caderno de Campo
- **Manual de Boas Práticas** (`docs/manual_boas_praticas.md`) recebeu **Seção 14** com dois novos padrões:
  - `14.1` — `*.tsbuildinfo` nunca deve ser versionado
  - `14.2` — Workbox SW auto-atualiza apenas quando o hash do bundle muda
- **Skill `vps-deploy`** recebeu:
  - Playbook 7 (Sincronização de Schema via `docker exec`)
  - Playbook 4 atualizado (Nginx + Certbot obrigatório)
  - Playbook 5 blindado (limpeza de `tsbuildinfo` antes do pull)
  - Armadilhas #1–#4 documentadas

## Impacto da Sessão 2
O ambiente de produção foi estabilizado após dois incidentes operacionais (HTTPS derrubado + deploy invisível). As lições foram imediatamente codificadas em skills e no Manual de Boas Práticas, criando guardrails que impedem a recorrência dos mesmos erros. A partir desta sessão, todo deploy segue o Playbook 5 blindado — com limpeza de artefatos, certbot e validação de HTTPS ao final.

## Sessão 3 — Refatoração de Navegação, Sincronia de API e Duplicação de Projetos

### 1. Refatoração da Cockpit Engineering UI
- **Navegação Breadcrumb:** Refatoração do `EngineeringNavigation.tsx` para o padrão `← Hub / PROJETO`. Melhora a orientação espacial do engenheiro e reduz a carga cognitiva.
- **Engineering KPI Strip (High-Density):** Otimização da barra de indicadores técnicos. Remoção de métricas puramente comerciais (ROI) da visão primária em favor de KPIs críticos de conformidade (kWp, FDI, Geração estimada).
- **Semáforo de Severidade:** Implementação de estados de severidade (ok, warning, error) baseados nas normas NBR 16690 para o FDI (110-135%) e status elétrico global.

### 2. Consistência e Sincronia de Rede (Sumaúma & Kurupira)
- **Correção de Health Check:** Identificado e resolvido erro 404 no monitoramento de saúde do Sumaúma. O backend foi atualizado para aceitar `/admin/health` (unificando com a `baseURL` do frontend) e o proxy do Vite foi validado.
- **Auditoria de Endpoints:** Verificação da consistência entre `NexusClient` (Kurupira) e `api.ts` (Sumaúma), garantindo que todos os prefixos de rota (`/api/v1` e `/admin`) estejam alinhados entre os ambientes de dev e produção.

### 3. Implementação da Duplicação de Projetos (Full Stack)
- **Backend (Kurupira):** Nova rota `POST /designs/:id/duplicate`. Implementada lógica de clonagem profunda via Prisma, preservando `designData` (JSON) e metadados estruturados, com prefixo automático `[CÓPIA]` e reset de status.
- **Frontend Service:** Atualização do `ProjectService.ts` e `NexusClient.ts` para suportar a nova operação, eliminando stubs e garantindo persistência real.
- **Hub UI:** Adição do botão **Duplicar** no `ProjectCardComponent`. Implementação de feedback de loading ("Clonando projeto...") e atualização reativa da lista após o sucesso.

### 4. Auditoria de Integridade e Mock Sweeper
- **Data Integrity Auditor:** Validação da "Cadeia da Verdade" para o novo card do Hub. O card agora exibe o **Nome do Projeto** como título primário e o **Nome do Cliente** como sub-legenda, resolvendo ambiguidades visuais em designs clonados.
- **Mock Sweeper:** Varredura completa nos fluxos de Salvamento, Criação e Duplicação. Certificado que todos os componentes de engenharia estão livres de `setTimeout` ou "falsos sucessos" — todas as ações estão vinculadas a mutações reais de banco de dados.

### 5. Correção de Bugs e UX
- **Fix ReferenceError:** Resolvido bug crítico onde `ProjectService` não estava importado no `ProjectExplorer.tsx`, impedindo ações de duplicação.
- **Busca Inteligente:** Atualização do filtro do Hub para incluir busca por `projectName`, permitindo encontrar duplicatas instantaneamente através da barra de pesquisa.

## Impacto da Sessão 3
A ferramenta de engenharia atingiu um novo nível de maturidade operacional. A duplicação de projetos permite que engenheiros realizem estudos de caso ("What-if analysis") de forma ágil, enquanto a refatoração da UI de navegação consolidou o padrão "Cockpit" de alta densidade informativa. A auditoria de integridade garante que o crescimento da base de dados (via cópias) não comprometa a rastreabilidade entre o motor de cálculo e a interface de usuário.
